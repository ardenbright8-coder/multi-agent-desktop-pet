# 看板派工

**一句话**：用户开执行窗口，调度把要求整理成工单和几捆任务；工兵占住整捆，每次只领一条，自测交报告后继续下一条，调度审核和小修，用户最后测试。

## 一、按活找文件

- 看规则是否覆盖真实场景：同夹 `考题（改完重考·看改没改坏）.md` 的「看板派工」几道。
- 查完整命令：仓库根 `AGENT_INTEGRATION.md`；执行入口 `scripts/bookmark-cli.mjs`。
- 换窗口交接：同夹 `交接单.md`。
- 一批 1～3 张写死的活、要一键全开给便宜 AI：同夹 `派活单.md`，不用成捆。

## 二、调度先整理再派

- [ ] ① 确认用户已经批准任务范围。原始需求和图片保留在原条目，不覆盖、不删；混着几个目标的长段，由调度整理成独立工单，不按逗号或字数机械拆。
- [ ] ② 每张工单只交一件能独立完成的事，写清目标、负责的文件/目录、具体做法、底线、测试方法、交付结果和依赖。每次领活只给当前这张，其他材料留看板。
- [ ] ③ 普通项目一个工兵做到底；复杂且能独立的部分才分给两个，最多三个。由调度分捆，工兵不自行拆队或启动其他模型。碰同一份文件或依赖上一条结果的活按顺序；并行写代码使用不同工作夹。
- [ ] ④ 把同一工兵的工单捆起来：用下面的 `dispatch bundle --ids … --name … --coordinator <调度窗口名>` 命令成捆，一批一条命令，第二批就是第二捆。（看板上 Ctrl 选中右键「捆成一捆」捆的是普通捆，不占整捆。）
- [ ] ⑤ 用户自己开新窗口（他在派活单上点「一键启动」也算他自己开，见同夹 `派活单.md`）。捆头只复制领取命令，不替用户启动窗口、子助手、命令行模型或后台工兵。每个执行窗口取唯一名字，重接旧窗口才沿用旧名字。

**算做完**：每捆负责谁、做什么、哪些文件、怎样验都明确；原话还在，领取命令只指向一捆。

## 三、工兵逐条做

- [ ] ① 按捆号领当前一条。整捆一旦归某窗口，其他窗口不能通过本捆或其中单条绕过占用；没领完当前条，再领仍是当前条。
- [ ] ② 只在本张工单范围内实现并测试，底线包括不碰系统/网络/账号/密钥、不改其他人的文件、不推送。未获授权的高危动作停下报告调度。
- [ ] ③ 自测完成后写报告：改了哪些文件、运行了哪些命令、实际结果、没有完成或需要决定的事。报告留“待审核”，不假造用户同意、不删除条目，整捆仍由原工兵占住。
- [ ] ④ 报告成功后自动敲同捆 `next` 领取下一条。不要用按组日常领活跳去其他项目；无待做条目时停止，这一捆留待调度审核。
- [ ] ⑤ 卡点说清楚并交给调度。需要换人先停写代码，再明确放回整捆，不能同时让两个窗口用同一个身份写码。

## 四、调度审核和用户测试

- [ ] ① 读取报告和代码，核对是否满足原需求、自测是否真实。一般小问题由调度直接修，不来回退工兵；严重跑偏才重新拆任务。
- [ ] ② 调度要写同一个工作夹时，先确认工兵已停写或交接，不跟仍在执行的窗口同时修改文件。修完复测。
- [ ] ③ 成品交给用户实际测试；待审核不等于通过。保留原任务、报告，用户明确通过以后，调度用 `dispatch accept` 及用户原话清理整捆；用户也可在捆头菜单亲自确认清理。未交报告或仍在干的捆不能清理。

**算做完**：代码经调度审过、问题修过、验证有证据；最后是否好用由用户测试确认。

## 五、命令示例

先把 `<CLI>` 换成本仓库 `scripts/bookmark-cli.mjs` 的完整路径。不要直接改私有 `bookmarks.json`，看板内存会覆盖。

```powershell
# 调度把已有工单捆起来；一捆中的顺序沿用看板显示顺序。
node "<CLI>" dispatch bundle --ids "任务甲,任务乙,任务丙" --name "字幕整理" --coordinator "Pi-调度甲"
# 调度查看捆号、归属、状态。
node "<CLI>" dispatch list --coordinator "Pi-调度甲"
# 用户开的工兵窗口：只领这一捆。
node "<CLI>" next "捆号" --by "工兵甲"
# 或在本调度、本助手组的空闲派工捆中选一捆；不拿其他组/调度的任务。
node "<CLI>" dispatch next --to "Pi Agent" --by "工兵乙" --coordinator "Pi-调度甲"
# 交当前条报告，再自动领本捆下一条。
node "<CLI>" report "条目号" --by "工兵甲" --text "改了A文件；运行测试X，全部通过；剩余问题无"
node "<CLI>" next "捆号" --by "工兵甲"
# 原工兵或调度明确放回整捆：先确认原窗口已停止。
node "<CLI>" dispatch release "捆号" --by "Pi-调度甲"
# 调度收完成消息；只取自己收件箱。消息离线保留，确认已收再清通知。
node "<CLI>" dispatch messages --coordinator "Pi-调度甲"
# 调度在自己窗口用工具执行等待；有新报告时返回给当前工具调用，最多等120秒。
# 这是一次普通命令，不启动模型、不挂后台工兵；超时后可再次等待。
node "<CLI>" dispatch wait --coordinator "Pi-调度甲" --seconds 120
node "<CLI>" dispatch ack "通知号" --coordinator "Pi-调度甲"
# 必须等用户测试通过，不得由工兵自己假造同意。
node "<CLI>" dispatch accept "捆号" --by "Pi-调度甲" --ok "用户测试通过的原话"
# 助手也可查询与技能页相同的完整正文。
node "<CLI>" dispatch skill 看板派工
```

## 六、坑清单

- 领取程序锁的是整捆，不只当前一条；报告后清的是这一条的在干标记，不是整捆归属。
- 窗口名是领取身份，要唯一；不能随便借另一个仍在运行的窗口名。
- 捆和拆条不同：几张工单装进一个捆；长需求要先由调度理解成工单。捆成一捆不会自动理解里面的长文字。
- 调度在自己窗口运行 `dispatch wait` 时，有报告就直接返回给该工具调用，助手接着审核；没运行等待时消息保留，之后用 `messages` 读取。没有接头的空闲窗口不能被凭空唤醒，不额外挂常驻后台工具。
- 普通捆/日常档仍用原来的确认流程；本技能只用于明确创建的多人派工捆。
